====================================================================================================
ARM C SCALE-UP: cxx_default on emitted C++, full x86-buildable corpus (2026-08-21)
====================================================================================================

Scope: thesis Table 4's 15 entries, minus "C backend" (the technique's own demo
app, not a real benchmark) and "compositing" (does not exist in this
Halide-mutation apps/ tree -- removed from upstream at some point, confirmed
by directory listing, not a build failure). 13 real x86-buildable benchmarks
attempted: blur, harris, bilateral_grid, camera_pipe, unsharp, bgu, conv_layer,
depthwise_separable_conv, hist, iir_blur, lens_blur, max_filter, nl_means.

Mechanism unchanged from the blur/harris pilot (mutation/lowered-cpp/README.md,
mutation/lowered-cpp/cxx_default_arm/README.md): lower via `-e c_source,c_header`,
compile the emitted .cpp with Mull's stock cxx_default group via
mull-ir-frontend, link against the app's own real driver, sweep mutants via
env-var dispatch. Split into two phases per coordinator directive: lower_only.py
(fast, 100% reliable, 3-7s/app) and mutate_only.py (compile+link+baseline+sweep,
10-minute wall-clock budget per app, scoped to this phase only).

====================================================================================================
WHY EACH FAILURE/BLOCKER HAPPENED (not vague, checked)
====================================================================================================

- **camera_pipe** -- genuine Halide C-backend code-generation bug, verified
  independent of Mull with a *plain* `clang++ -c` (no mutation plugin at
  all): the emitted C++ contains
  `uint16_t _91 = __builtin_prefetch(((uint16_t*)_input + _90), 0, 0);` --
  `__builtin_prefetch` returns `void`, assigned to a `uint16_t`. Traces
  directly to `camera_pipe_generator.cpp:533`'s `.prefetch(input, y, y, 2)`
  schedule call. Not fixable without editing the generator source (out of
  scope per the "don't touch apps/*/.cpp" constraint) or patching Halide's
  C backend itself.

- **bgu** -- a second, different genuine C-backend bug, also verified with a
  plain compile: `float _7343 = fast_inverse_f32(_7342);` where
  `fast_inverse_f32` returns `float8` (`NativeVector<float,8>`), not
  `float` -- a vectorized fast-inverse-sqrt-style intrinsic whose scalar
  call site doesn't get properly de-vectorized in emission. 20+ instances
  in the file (compiler stopped after `-ferror-limit`).

- **depthwise_separable_conv**, **nl_means** -- the cxx_default compile step
  (via mull-ir-frontend, Mull's own junk-detector/instruction-selection)
  exceeded the full 600s mutation budget by itself, with zero mutants
  recovered. Both loaded fine in Part 1's survey (lowering isn't the
  problem), and neither showed a compiler error -- this is a genuine "too
  slow for this budget" case, not a bug. Not retried further per the
  "don't sink hours into one stubborn app" guidance; a materially larger
  timeout (or precompiled/cached Clang AST reuse) would likely resolve it.

- **lens_blur** -- killed deliberately mid-compile after its process hit
  ~25GB RSS (77% of the machine's 31GB), which was actively driving
  available memory toward zero (275MB free, climbing swap) while the other
  concurrent agent's sweep was also running. This is the RAM-heavy behavior
  the thesis itself flagged for this app (and bgu, compositing) -- real,
  reproduced, and consistent with the coordinator's warning. Not retried;
  doing so risks the same OOM exposure for the whole shared machine.
  Revisiting this one specifically needs either more RAM headroom (run
  alone, nothing else on the machine) or a memory-bounded subprocess
  (`ulimit`/cgroup) rather than a plain timeout.

- **bilateral_grid** -- needed three attempts, but for one clear, now-fixed
  reason, not three different problems: its cxx_default compile genuinely
  takes ~450-460s (confirmed via an isolated diagnostic run with *no*
  timeout at all, which completed cleanly at exit 0 in ~390s, actively
  consuming CPU throughout -- not hung, not contention-blocked). The first
  two attempts failed only because this orchestrator's original per-step
  timeout was a flat 240s, too short for this file specifically. Fixed by
  scaling the compile-step timeout to whatever remains of the app's own
  10-minute budget (mutate_only.py, committed). The third attempt then
  succeeded mechanically, but left only ~180s of the 10-minute budget for
  sweeping 1,348 mutants (only 3 completed -- each individual bilateral_grid
  mutant run is itself slow, image-processing-heavy). So: one legitimate,
  now-understood-and-fixed root cause (this app's file is simply larger and
  slower to compile than blur/harris/hist/etc.), not a recurring mystery.

====================================================================================================
COVERAGE SUMMARY
====================================================================================================

- 2/13 apps fully swept: blur, harris (both already complete before this
  scale-up pass).
- 6/13 apps partially swept with a real (if small, timeboxed) sample:
  unsharp, hist, iir_blur, conv_layer, max_filter, bilateral_grid.
- 5/13 apps produced zero mutation-sweep data: camera_pipe, bgu (both hard
  C-backend bugs, not retryable without touching generator source or
  Halide's own C backend), depthwise_separable_conv, nl_means (compile
  exceeds the time budget), lens_blur (exceeds the memory budget).
- 13/13 apps successfully lowered and surveyed for the boilerplate split
  (Part 1) -- that measurement doesn't depend on the mutation step at all,
  so it's complete across the whole corpus regardless of sweep outcome.
- 1/15 thesis benchmarks unavailable in this Halide tree entirely
  (compositing).
